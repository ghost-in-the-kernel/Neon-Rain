# theGhost.md: every decision Neon Rain stands on

The layer beneath the comments. Each decision has a number (R-001), what was decided, why, what holds
it (a test, a document, a file), who decided and when, a status, and the decisions it touches. A new
decision is appended; a reversed one is marked `superseded by R-nnn` in the same commit that adds its
successor, and the successor names it. `test/test_ghost.py` holds this file: ids unique and
sequential, supersession named on both sides, and no two in-force decisions tagged with the same
`subject:` that carry a `conflicts-with:` line (docs/ROADMAP.md, P-05).

Statuses: `proposed`, `in force`, `superseded by R-nnn`, `withdrawn`, `refused` (decided against, so
the question is closed).

Who may write here: Ghost decides. Any agent may append a decision Ghost has made, and may add or
correct cross-references (`See also`, `Held by`) on any entry without asking. A change to an entry's
`Decision`, `Why` or `Status` text is Ghost's alone, or an agent's with Ghost's explicit word in the
same session. A `proposed` entry is a recommendation waiting on Ghost; nothing is built on it until
it is `in force`.

### R-001: Python 3.12, PyTorch, and the scientific stack
- **Decision:** The harness, the data pipeline, the features, the models and the scorer are Python
  3.12. PyTorch for the network; polars for frames (pandas only where a library demands it); LightGBM
  for the tree baseline; pytest for tests. Dependencies pinned in `requirements.lock` and installed
  only from it. No notebook is a source of truth: a notebook may explore, but every number in a
  document comes from a script under `scripts/` or `neonrain/`.
- **Why:** Ghost's languages are C#, Java and C++, and this is the one project where that does not
  decide it: every backtesting, time-series and gradient-boosting library worth comparing against is
  Python-first, and a Java reimplementation would spend the budget rebuilding tools instead of
  testing the thesis. The agents doing the implementation write Python fluently. Lockfile-only
  install is the supply-chain rule (docs/SUPPLY-CHAIN.md).
- **Held by:** `requirements.lock`; `scripts/precommit.sh` refuses an import not in it;
  `test/test_supply_chain.py`.
- **Source:** proposed by Claude Fable, 2026-10-22; decided by Ghost, 2026-10-22: "lets do python.
  the drawback is my ability to audit code by hand, so I am going to be relying more heavily on
  testing here." That drawback is answered by R-015.
- **Status:** in force
- **See also:** R-003, R-009, R-015
- **subject:** toolchain

### R-002: The harness before the model, and the harness is frozen before the first model trains
- **Decision:** Nothing under `neonrain/models/` is written until `neonrain/harness/` passes its
  adversarial tests (ROADMAP phase 1): a deliberately leaking feature is caught; a survivorship-biased
  universe is caught; a strategy with zero true edge reports a Sharpe within its noise band after
  costs; the number of trials is counted and reported. Once phase 1 closes, the harness's evaluation
  code changes only in a commit that re-runs every baseline and shows every golden unchanged.
- **Why:** The failure mode of every retail quant project is a backtest that lied, found out with real
  money. Katana's P-01 (the oracle before the compiler) is the same rule: a wrong answer must be
  catchable by a run before the thing that could be wrong exists. Here the wrong answer is a
  too-good backtest, and the only defence is a harness built to catch it that cannot be quietly
  adjusted afterward.
- **Held by:** `test/test_harness_adversarial.py`; `harness/goldens/` (baseline results, byte-identical
  after any harness change); `docs/HARNESS.md` (HAR-01 onward).
- **Source:** Ghost, 2026-10-22 ("build a rigorous backtesting harness first, then the dumbest
  baseline, then add features one at a time").
- **Status:** in force
- **See also:** R-004, R-005, R-007
- **subject:** method

### R-004: Four horizons, cross-sectional, direction and rank, never price
- **Decision:** The targets are, for each ticker and each trading day *t*, the forward return over
  3 trading days, 5 trading days (one week), 21 trading days (one month) and 63 trading days (three
  months), each expressed two ways: direction (sign of the excess return over the universe median
  that day) and cross-sectional rank (percentile among the universe that day). The model never
  predicts a price level or a raw return. Every horizon has its own head; the heads share a trunk.
- **Why:** Cross-sectional prediction (which stocks beat which) is where the literature finds what
  little signal there is; absolute return prediction is dominated by the market factor and noise.
  Direction and rank are scale-free, so the same metrics work across the four horizons. Ghost named
  the four horizons as the project's benchmarks, 2026-10-22.
- **Held by:** `neonrain/targets.py` (one function per horizon, pure); `docs/HARNESS.md` HAR-02;
  `test/test_targets.py` (a known price series yields the hand-computed labels).
- **Source:** Ghost (the horizons), 2026-10-22; the cross-sectional framing on recommendation.
- **Status:** in force
- **See also:** R-002, R-005
- **subject:** target

### R-005: Walk-forward only, purged and embargoed, every trial counted
- **Decision:** Evaluation is walk-forward: train on `[start, t)`, predict on `[t + embargo, t +
  step)`, roll. The embargo is at least the longest horizon (63 days) so no training label overlaps a
  test window. No random k-fold, ever. Every evaluation run writes a line to `harness/trials.tsv`
  (git-tracked) with the config hash, the metric, and the count of trials so far; the deflated Sharpe
  ratio reported alongside any Sharpe uses that count. A metric with no trials line does not exist.
- **Why:** Random splits on time series leak the future into training through overlapping labels and
  autocorrelation; the walk-forward with purge and embargo is the standard (López de Prado, *Advances
  in Financial Machine Learning*, ch. 7). Counting trials is the only defence against selection bias:
  the best of a hundred backtests is expected to look good by chance.
- **Held by:** `neonrain/harness/split.py`; `test/test_harness_adversarial.py` (a label that leaks
  across the embargo is caught); `harness/trials.tsv` and `test/test_trials.py` (every result in
  `docs/RESULTS.md` has a trials line).
- **Source:** on recommendation, 2026-10-22.
- **Status:** in force
- **See also:** R-002, R-004
- **subject:** method

- **Decision:** `data/` is ignored by git. Every dataset has a fetch script under `scripts/fetch/`

### R-007: Baselines first, and the tree model is a baseline the network must beat
- **Decision:** Before any network: (a) zero (predict the universe median), (b) 12-1 momentum, (c)
  short-term reversal, (d) LightGBM on the same features the network will see. Each is run through
  the harness at all four horizons and its result frozen as a golden. The network is reported against
  (d) first. A network that does not beat (d) out of sample after costs is a finding (docs/FINDINGS.md),
  and the project's honest result until it does.
- **Why:** Gradient-boosted trees are the empirical winner on tabular financial features in most
  published comparisons; a network that cannot beat them is adding cost, not signal. Ghost's own
  framing (2026-10-22): "try the dumbest possible baseline, then add features one at a time and see
  what survives."
- **Held by:** `neonrain/baselines/`; `harness/goldens/baseline_*.json`; `docs/RESULTS.md`.
- **Source:** Ghost, 2026-10-22.
- **Status:** in force
- **See also:** R-002, R-009
- **subject:** method

### R-008: News is scored once by a pinned Haiku, into an append-only ledger, point-in-time
- **Decision:** A news story is read by exactly one model, Claude Haiku at a pinned model ID
  (`claude-haiku-5-5` at the ID the ledger records), with a versioned prompt, temperature 0, and a
  fixed output schema: tickers mentioned, a bullish/bearish score on a 1–10 scale per ticker, a
  confidence, and a one-line reason. The result is appended to `ledger/news.parquet` keyed by story
  hash with the story's **publish** timestamp (never the fetch or scoring time), the prompt version
  and the model ID. A story is never re-scored under the same prompt version; a new prompt version
  scores into new rows and the old rows stay. Features are built from the ledger alone, using only
  rows whose publish time precedes the feature date. The predictor never calls a model.
- **Why:** Ghost's design (2026-10-22): a Haiku agent reads a story and returns bullish/bearish on a
  ten-point scale and which stock it was for. Pinning and ledgering make the scorer a deterministic
  feature extractor rather than a live dependency: the pipeline is reproducible given the ledger, the
  harness can be re-run without API cost, and a prompt change is an experiment with its own trials
  line, not a silent drift. Publish-time keying is the leakage rule: a score known only after the
  outcome is lookahead. Cost at Haiku 5.5 list price is about $0.0001 per thousand-token story, so a
  million stories is on the order of $100 plus output; affordable, but the ledger means it is paid
  once.
- **Held by:** `neonrain/scorer/` (the only module that imports a model client; `docs/modules.json`
  MOD-01); `ledger/` schema in `docs/LEDGER.md` (NL-01 onward); `test/test_ledger.py` (append-only;
  a row dated after its story's publish time is refused; a feature built from a future row is caught
  by the adversarial test).
- **Source:** Ghost, 2026-10-22, with the ledger discipline from Katana R-030.
- **Status:** in force
- **See also:** R-002, R-005, R-009
- **subject:** news

### R-009: One network until the tabular trunk is proven; its shape is a decision, not a search
- **Decision:** The first network is one architecture, chosen in phase 4 by a decision here, trained
  on the same feature table the tree baseline sees, with per-day cross-sectional normalization and
  four heads. Architecture search, ensembles, attention over the whole universe, and anything that
  takes "all tickers as input neurons" at once are refused until that network has beaten R-007(d) at
  one horizon out of sample. Ablations are run one feature family at a time with a trials line each.
- **Why:** Ghost's first sketch had every ticker as an input neuron; with a few thousand daily
  samples per name that is a memorization machine. Pooling across tickers with per-name features is
  the shape that generalizes. Katana P-04 (one target until the shape layer is proven) is the same
  rule: breadth after depth.
- **Held by:** `docs/ROADMAP.md` §3; `neonrain/models/` (one model file until this is superseded).
- **Source:** on recommendation, 2026-10-22.
- **Status:** in force
- **See also:** R-007, R-008
- **subject:** model

### R-014: Held-out ticker groups are the second evaluation axis; dispersion is reported with the mean
- **Decision:** Every evaluation is a grid of two splits: walk-forward in time (R-005, primary) and
  held-out ticker groups (the universe partitioned into *k* groups by a fixed seeded hash of the
  ticker, each group held out in turn, the model trained pooled on the rest). A result reports, per
  horizon, the mean metric and its dispersion (standard deviation and range) across held-out groups
  and across time folds. A result whose dispersion across groups is wide relative to its mean is
  reported as "fits names, not an algorithm" and does not count as beating a baseline. Training on
  a single ticker is refused: the unit of generalization is a group of names, never one.
- **Why:** Ghost, 2026-10-22: test on one stock, then another, and use the variance of accuracy to
  tell whether we trained to fit the data or trained an algorithm. The variance idea is the right
  one and is the only direct test of name-memorization. The ticker axis cannot replace the time axis
  (an unseen name's prices on the same dates share the market factor with the trained names, so time
  still leaks), and one name is too few samples to train on, so it is the second axis, not the
  first. (The underlying technique is leave-one-group-out cross-validation; the dispersion report is
  the project's own rule.)
- **Held by:** `neonrain/harness/split.py` (`ticker_groups`); `docs/HARNESS.md` HAR-05;
  `test/test_harness_adversarial.py` (a model that memorizes a name shows the dispersion signature);
  `docs/RESULTS.md` (every result has both axes).
- **Source:** Ghost, 2026-10-22; shaped on recommendation.
- **Status:** in force
- **See also:** R-005, R-007
- **subject:** method

### R-015: Tests are the audit: mutation-tested, readable Python, and the mirror written blind
- **Decision:** Because Ghost cannot audit Python by eye the way he can Java, the tests carry the
  audit. (a) Every unit test runs through mutation testing (`mutmut`, in `scripts/precommit.sh`);
  a surviving mutant gets a test that kills it or a one-line write-up in `docs/MUTATION.md` saying
  why it is harmless, as Suite Builder does with Stryker. (b) Code is written to be read by a
  non-Python reader: type hints on every function, no comprehension over three clauses, no
  decorator magic, no `*args/**kwargs` in our own signatures, no operator overloading beyond what a
  library forces, one concept per function under 40 lines, and a docstring that says what the
  function returns for a concrete input. (c) The independent reimplementations the harness's mirror
  tests compare against (ROADMAP 1.6) are written by an agent that has not seen the code under test,
  from the contract in `docs/HARNESS.md` alone. (d) Every number Ghost is asked to trust has a test
  that computes it by hand on a ten-row example he can check in a spreadsheet.
- **Why:** Ghost, 2026-10-22, on choosing Python: he will rely more heavily on testing here. A test
  suite that mutation cannot break is the closest thing to a second reader; readable code is the
  second; a blind mirror is the only check on the harness's own arithmetic (Katana: a reimplemented
  oracle agrees with its twin on every shared mistake). (d) is how the non-Python program director
  stays the project's first reviewer, as he is Katana's.
- **Held by:** `scripts/precommit.sh` (mutation score reported; a surviving mutant with no
  `docs/MUTATION.md` line fails); `docs/MUTATION.md`; a lint rule for (b) in `pyproject.toml`
  (phase 0.5); `test/test_harness_adversarial.py` for (c).
- **Source:** Ghost, 2026-10-22; shaped on recommendation.
- **Status:** in force
- **See also:** R-001, R-002, R-012
- **subject:** method

### R-016: Data and artifacts arrive through GitHub as plain git blobs; nothing is fetched live from the workspace
- **Decision:** (a) Datasets are obtained by Ghost (downloaded on his machine or elsewhere with
  network access) and pushed to a separate private data repository, `ghost-in-the-kernel/neon-rain-data`,
  as plain git files under 100 MB each (parquet, chunked by year or by ticker range when larger).
  (b) The artifact store of R-010 is a second private repository, `ghost-in-the-kernel/neon-rain-artifacts`,
  same rules, content-addressed: each file is named by its SHA-256 and the main repository records
  the hash it depends on. (c) `scripts/fetch/<dataset>.py` of R-006 clones or pulls the data
  repository and verifies the manifest hash; it never reaches any other host. (d) The license of
  every dataset is checked by Ghost before it enters the data repository; the manifest line says
  so. Until a news feed is supplied the same way, phase 5 is blocked and phases 1–4 proceed.
- **Why:** NR-F-01: from this workspace every market-data and news host is refused, GitHub Releases
  and LFS uploads are refused for this session type, and plain git pushes are the one write that
  works. A second repository keeps blobs out of the code repository's history (R-006's reason) and
  keeps the main clone small for the agent (AGT-01). Hash-naming makes artifacts immutable and
  cheap to verify.
- **Held by:** `scripts/fetch/`; `data/MANIFEST.md` (a `supplied by` column); `test/test_manifest.py`
  (every line has a hash and a license); `scripts/probe/reachability.py` (re-run at every phase
  boundary; a newly reachable host is a journal entry, not a silent change of route).
- **Source:** measured by Claude Fable, 2026-10-22; decision proposed for Ghost's word.
- **Status:** proposed
- **See also:** R-003, R-006, R-010

### R-017: The lock is compiled by `uv pip compile`; `pip` installs it
- **Decision:** `requirements.lock` is compiled from `requirements.in` with `uv pip compile
  --generate-hashes --python-version 3.12`, and installed with `pip install --require-hashes -r
  requirements.lock`. uv is a tool the session already carries, not a dependency of the project:

### R-018: A dependency enters the lock in the phase that first imports it, and no version younger than seven days
- **Decision:** (a) `requirements.in` keeps all ten direct dependencies with their reasons, but a
  dependency is commented out, and so absent from `requirements.lock`, until the phase that first
  imports it: torch at phase 4, anthropic at phase 5. Uncommenting one is that phase's first commit
  and recompiles the lock. (b) The lock is compiled with `--exclude-newer` seven days before the
  compile date, so no release younger than a week enters it.
- **Why:** (a) PyPI's Linux torch wheel brings about 3 GB of CUDA libraries and the CPU-only index
  is refused from the session (J-009); carrying them from 0.5 costs every session's disk and
  install time for nothing, and every package not installed is one not attacking us. (b) A
  malicious release is usually found and pulled within days; the cooldown is Suite Builder's
  G-256 carried over.
- **Held by:** `requirements.in`; docs/SUPPLY-CHAIN.md rule 2; `test/test_supply_chain.py` (an
  import under `neonrain/` that the lock lacks fails it).
- **Source:** proposed by Claude Opus, 2026-10-22; Ghost, 2026-10-22: "go with your calls".
- **Status:** in force
- **See also:** R-001, R-017
